# 개발 과정과 설계 선택

## 내부 RAM에 사진 전체를 담지 않는 방법

320×240 RGB565 사진은 153,600바이트입니다. STM32F103RB에서 이 사진 전체를 RAM으로 옮기는 대신 ArduChip의 외부 FIFO에 보관하고, Zynq가 요청할 때 2 KB씩 읽도록 구성했습니다. 첫 CHUNK에서 FIFO burst read를 시작하고 마지막 청크까지 카메라 CS를 유지해 FIFO 읽기 포인터를 연속으로 진행합니다.

이 선택은 사진 보관 위치, 전송 단위, 응답 버퍼 크기를 함께 정해야 하는 문제였습니다. 최종 부록 양쪽 코드에는 153,600바이트와 2,048바이트·75청크 관계가 정의돼 있습니다.

## SPI 응답 준비와 읽기 시점을 분리

STM32가 카메라 FIFO를 읽어 응답을 준비하는 동안 Zynq가 SPI 클록을 먼저 공급하면 준비되지 않은 응답을 읽을 수 있습니다. 명령 transaction과 응답 transaction을 분리하고 READY 신호를 DMA 등록 뒤 올리는 방식으로 준비 조건을 정의했습니다.

보고서의 `SPI2_PrepareResponse`는 READY를 내리고 DMA 등록을 시도합니다. 실패하면 명령 수신 상태로 복구하며, 성공한 뒤 READY를 올립니다. ISR에서는 명령과 플래그를 전달하고 캡처·FIFO 읽기 등 긴 처리는 main loop에서 수행합니다.

이 준비 조건은 보고서 코드에서 확인할 수 있습니다. 수정 전후 전송 성공률을 비교한 별도 측정치는 보관 자료에서 확인되지 않았습니다.

## 사진의 처리 순서와 데이터 사용 기간

수신·판별·저장을 태스크로 분리했지만, 동일 사진 버퍼를 여러 프레임이 병렬로 사용하는 구조는 아닙니다. RxTask가 사진을 받으면 포인터와 ID를 queue로 전달하고, SaveTask가 저장 또는 생략을 완료해야 다음 프레임을 받을 수 있습니다.

ISR에서 긴 수신·추론을 하지 않고 semaphore를 전달한 뒤 종료합니다. 각 태스크는 입력 객체에서 대기하며 실제 데이터가 도착했을 때만 진행합니다. 우선순위 숫자와 별도로 semaphore/queue가 실행 조건을 정합니다.

## 학습 입력을 C 추론에 맞추기

카메라의 RGB565 사진을 학습 모델의 1×64×64 grayscale 입력으로 변환하고, PyTorch와 C에 같은 정규화 범위 [-1,1]을 적용했습니다. 모델 가중치를 C float 배열로 내보내 Zynq PS에서 실행하는 경로를 구성했습니다. Python/PIL과 C의 resize·grayscale 수치가 동일한지는 재현 시 별도 대조할 항목입니다.

최종 보고서 부록에서는 background 확률로 배경을 먼저 걸러낸 뒤, FC1 embedding의 owner template 유사도로 소유자를 구분합니다. 따라서 PC의 3클래스 validation 결과만으로 이 최종 분기의 정확도를 설명할 수 없습니다.
